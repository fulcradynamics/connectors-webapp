# Attio ↔ Fulcra: typed fields and preserved note revisions

Date: 2026-11-02. Status: implementation authorized by Ash’s subsequent “build attio” request. Existing account collection still requires explicit source/field selection and protected credentials. The user also requested a new demo workspace when none existed.

## Intent and approach

Extend the existing connector template so selected Attio records and list entries have editable, typed Fulcra working copies, with verified updates in both directions. Import selected records' notes as inspectable source snapshots. Send edited note text back as linked revision notes while retaining the original note and its rich content in Attio. Keep the existing Sources → Destination → Schedule → Preview/Enable experience, owner authentication, encrypted grants, native controller identity, v1 Event records, folders, and shared persisted runner. No annotations, separate database, user-managed cron, or AI interpretation of CRM content is required.

Three approaches were considered. A read-only importer is useful but does not meet the requested two-way behavior. Replacing complete record/note snapshots is simple but risks erasing unselected fields or rich note content. The recommended approach uses explicit typed-field updates and an append-only note revision lineage. It is more work to represent conflicts and revisions, but its write scope is reviewable and the original note remains intact. This recommendation requires review before implementation.

The first release is a bounded working set, not an account-wide CRM mirror. Ship the first implementation increment for existing People and Companies plus their explicitly selected note lineages. The typed object contract also covers Deals, custom objects and existing list entries, but those editors are a subsequent increment and must pass the same schema codec matrix before being enabled. Record creation is a separate opt-in capability. Do not create lists, attributes, options, statuses, pipelines, records referenced by other fields, or workspace members implicitly. Tasks, email, comments, meetings, recordings, files/attachments, workflows, schema editing, merging records, and destructive provider deletion are outside this release.

“Two-way” has two precise meanings: selected typed fields update their existing Attio entity in place; edited note text creates a linked Attio revision note. It does not mean arbitrary rich-body note replacement or complete workspace replication.

## Prior art and verified API constraints

The reviewed prior art is `keng009/fulcra-sales-memory` at `53d0c6847b517c2e41fdd728e48a3011813b0cd8`. It is a Claude instruction packet, not an executable Attio adapter. Its useful patterns include stable source identities, provenance, independent destination reconciliation, duplicate checks, and readback. Its primary direction is Fulcra → CRM; separate selected CRM-note imports are not a two-way native sync engine. Its dated manual test reports do not establish this connector's behavior. The upstream working-set policy also does not authorize collecting the complete contact graph.

Upstream is MIT, copyright 2026 Nick Kengmana / Fulcra Dynamics. Preserve its copyright and permission notice with any substantial copied/adapted material. Prefer an independently implemented adapter and an attribution note identifying the pinned design reference; do not adopt upstream AGENTS/SKILL instructions or annotation storage.

Current official documentation checked for this draft:

- [Authentication](https://docs.attio.com/rest-api/guides/authentication) supports single-workspace API keys and OAuth; the latter is preferred for multi-workspace applications.
- [Identify](https://docs.attio.com/rest-api/endpoint-reference/meta/identify) is `GET /v2/self`. A revoked, unknown, or deleted token can return HTTP 200 with `active: false`; only `active` is guaranteed present. Do not equate HTTP success with valid credentials.
- [Record overwrite](https://docs.attio.com/rest-api/endpoint-reference/records/update-a-record-overwrite-multiselect-values) uses PUT on the existing record ID; supplied multiselect values replace/remove existing values. PATCH appends multiselect values. The documented 409 concurrent-write error is not evidence of a caller-supplied compare-and-swap precondition.
- [Entry overwrite](https://docs.attio.com/rest-api/endpoint-reference/entries/update-a-list-entry-overwrite-multiselect-values) supplies corresponding PUT semantics for existing list entries.
- [Attribute discovery](https://docs.attio.com/rest-api/endpoint-reference/attributes/list-attributes) exposes typed schema, stable attribute IDs, writability, required/unique/multiselect/archive flags and configuration. Slugs and labels are presentation aids; IDs bind mappings.
- [Note reads](https://docs.attio.com/rest-api/endpoint-reference/notes/get-a-note) expose Markdown/plaintext projections. [Note updates](https://docs.attio.com/rest-api/endpoint-reference/notes/update-a-note) replace the whole note content when content is provided; omitted fields remain untouched, and note parent cannot change. [Attio's note editor](https://attio.com/help/reference/productivity-collaborating/notes) supports images. The API representation must therefore be treated as potentially lossy; this draft does not claim that images or arbitrary rich blocks round-trip through Markdown.
- [Note creation](https://docs.attio.com/rest-api/endpoint-reference/notes/create-a-note) accepts a parent record and a declared content format. [Note listing](https://docs.attio.com/rest-api/endpoint-reference/notes/list-notes) can be bounded to a parent record, with pagination; do not call an unfiltered workspace-wide note scan.
- [Rate limits](https://docs.attio.com/rest-api/guides/rate-limiting) document 429 responses and a Retry-After HTTP date. A numeric-only Retry-After parser is insufficient.

These are documentation observations. All account-specific permissions, schema behavior, note rendering/image preservation, and create/recovery semantics remain live-test obligations.

Token replacement must match the bound workspace; a different workspace requires a separate connection. One owner's key, grant, controller, or journal must never be copied to another deployment.

Provide the official [API-key management help](https://attio.com/help/reference/apps/generating-an-api-key) beside both new and saved credentials. The documented native path is workspace menu → Workspace settings → Developers → + New access token → name the token → set Scopes. An Attio workspace admin is needed to create/manage keys; the help page says keys are available on all plans. Do not invent a universal deep link or final Save button label: verify the current confirmation control in the actual UI and record its exact label before shipping onboarding. Explain how to edit scopes or delete the key from the same Developers screen. Label API documentation separately from credential management.

Validate with GET self, requiring `active === true`, a valid stable workspace ID, supported token level, and enough demonstrable scope for the enabled capabilities. Missing identity/scope fields are an incomplete validation result, never guessed from optional `sub` or display names. Show workspace name/slug only as labels. Bind workspace ID into every mapping, source identity, operation, and grant context. Repeat validation on reconnect and after authorization failures; fail closed on an active:false 200 response. No refresh-token behavior is invented for manually generated API keys.

## Source identities, typed representation, and write contract

Canonical keys include workspace UUID, object/list UUID, entity UUID, kind, and connection namespace. Record references carry target object and record UUID, not a name/email match. Notes carry parent object/record and note UUID. Fields bind attribute UUID; option/status fields bind option/status UUID. Changing a slug, label, or display order must not reroute a write. Record/list entry and note IDs are not interchangeable.

Use a versioned managed JSON working document with immutable server-owned bindings, schema fingerprint, protected read-only projection, and an explicit editable-values map keyed by selected attribute IDs. Validate browser edits, API commands, and direct Fulcra file edits with the same server contract. Reject unknown fields, unsafe keys, non-JSON data, forged IDs, changed parent/workspace/object, unauthorized attributes, invalid encodings, and oversized inputs. The server never accepts a caller-supplied provider path or an arbitrary immutable-file reference.

Keep provider responses and the editable projection distinct. Provider metadata such as actors, active_from/active_until, source, and history must not be replayed as writable field values. Import current values using the documented active-value semantics and preserve supplied history as read-only source evidence where requested/supported. Do not call the history-replacement/migration APIs to perform ordinary field edits. Never infer writable permission just because a field has a familiar name or type.

Proposed folder layout is `<destination>/live/<connection-UUID>/index.md`, `records/<local-UUID>.json`, `entries/<local-UUID>.json`, `notes/<local-UUID>.md`, `.conflicts/<conflict-UUID>/...`, and `.sync/create/<operation-UUID>.json`. These are scoped working/evidence paths, not editable routing instructions. A v1 Event revision carries schema version, workspace/object/list/entity identity, source kind, source semantic hash, operation/revision identity, producer, source occurrence time when known, observed/recorded time, direction, verified outcome, and the permitted typed projection or immutable snapshot references. Never invent an occurrence time from import time. Its deterministic revision ID includes owner/connection/source identity and semantic source version; re-reading the same version must not emit another Event. The inline type creator must validate this exact connector-compatible v1 schema before selection.

| Type family                                                  | Initial write codec and semantic comparison                                                                                                                                                                                                                           |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Text, checkbox, number, rating                               | Explicit scalar or ordered collection per schema; enforce provider constraints, finite numeric values, and boolean false versus absent. No truthiness-based clearing.                                                                                                 |
| Date and timestamp                                           | Date remains a calendar date without timezone conversion; timestamps require an explicit timezone/offset and compare at documented precision. Preserve user/source occurrence time separately from recorded/imported time.                                            |
| Currency                                                     | Structured amount plus allowed currency code/attribute configuration; no conversion or rounding beyond an explicitly documented codec.                                                                                                                                |
| Email, domain, phone                                         | Structured values using Attio's documented shape and region requirements. No invented country code or destructive email normalization. Compare provider-confirmed canonical forms.                                                                                    |
| Personal name and location                                   | Preserve supported components; no string splitting, geocoding, or erasing unknown components. Until the compound codec proves complete, expose read-only instead of sending a partial structure.                                                                      |
| Select/status, including deal/list stage                     | Existing allowed option/status IDs only. Changing a stage is a real CRM write shown explicitly in preview; no guessed label matching, new options, or pipeline restructuring.                                                                                         |
| Record references                                            | Existing UUIDs within explicitly approved target-object/reference scope only. No `if_unmatched:create`, name matching, or implicit contact/company creation. Declare reciprocal relationship effects in preview; decline writes whose side effects cannot be bounded. |
| Actor/interaction, system/enriched/nonwritable/unknown types | Import protected; no write codec in this release. A later codec requires its own demonstrated API round-trip and permission tests.                                                                                                                                    |

First-release two-way acceptance requires text, checkbox, numeric, date/timestamp, existing select/status, and existing record-reference codecs; compound types can ship read-only with a precise reason until verified. Unsupported values remain visible as protected snapshots where they fit the bounds, never silently omitted and then cleared.

An omitted editable attribute means unchanged. Clearing is a separate explicit operation translated into the exact tested empty-value shape; required attributes cannot be cleared. A multiselect edit is a complete replacement of that one selected attribute, including intended removals, using PUT; PATCH append is not the generic sync algorithm because retries could duplicate values. Send only changed permitted attributes, never the full fetched values object. Test that omitted attributes and unselected collection members outside the edited field are untouched. Collection ordering and equality are codec-specific: never sort all arrays indiscriminately or collapse distinct values by display label.

Schema type/cardinality/writability/option changes invalidate queued writes for the affected field. Preserve accepted text/values and show a schema conflict. Renames can update display labels through stable IDs. Archived/removed attributes do not authorize recreating schema. Unknown schema responses or incomplete value pages pause the affected entity without advancing its baseline.

## Rich notes: preserve source and publish linked text revisions

Never PATCH `content` on an imported source note in this release, even if its Markdown appears simple. Absence of an image marker is not proof that hidden rich content is absent. Keep the original rich note in Attio untouched, preserve exact API-visible Markdown/plaintext/tags/metadata in immutable Fulcra snapshots, and link to the original Attio record/note using verified returned or documented URLs. Mark the import as an API text projection, not a full image/file backup. Do not claim to have downloaded unavailable image bytes or fetched arbitrary source URLs.

A Fulcra note editor shows the source snapshot separately from an editable text-revision draft. Saving the draft publishes a new note on the same authorized record, with a human-readable revision title, deterministic operation marker, original note identity, predecessor revision identity, producer, evidence, and recorded-at timestamp. The marker is plain data, not authorization. The original note is not rewritten, deleted, or retagged. The new revision links back to its source through supported links and identifiers; if there is no verified note deep-link format, use the record link plus exact note identifier rather than inventing one.

Every later accepted text change creates another immutable revision note. Attio-side edits to original/revision notes are reimported as new observed versions and reconciled against the chosen text baseline. A revision chain can branch; concurrent branches require review, not a guessed latest title/date. Connector-owned revision IDs and complete marker validation prevent an imported revision from being re-exported as another note. A third-party marker/title is not enough to bind a mapping: validate workspace, exact parent, operation, source lineage, and payload fingerprint.

If the original note or current revision changes while a draft is pending, retain both visible text versions and require an explicit current reviewed resolution before publishing. An owner can choose fresh Attio text, accepted Fulcra text, or a retained intervening working-file version. The selected text becomes a new linked revision; it never becomes permission to replace rich source content. Protected/unknown metadata always comes from a fresh provider read. Title-only edits follow the same append-only revision path; the imported original's title remains intact.

Live API readback can remove empty paragraph lines. Verify exact original payload/provenance and only a narrowly expected paragraph serialization; canonicalize the working copy to the verified returned API projection. Retain the original accepted draft in immutable attempt evidence, its reference and original/observed payload hashes. Persist the exact observed footer for no-echo reads. Do not treat whitespace normalization as general Markdown semantic equivalence; unverified complex serialization remains uncertain without replaying creation.

## Reconciliation, conflicts, and accepted-work durability

Maintain baselines per writable attribute and per note text lineage, plus hashes/references for protected source evidence and verified Fulcra versions. Use stable semantic values, not response key order, slugs, timestamps alone, or display labels. Reconcile each destination independently; a failed v1 event/file write must not cause an already confirmed Attio mutation to repeat.

For a field: unchanged/unchanged is a no-op; Attio-only change pulls; Fulcra-only change pushes after a fresh schema/scope/value read; equal changes converge without another write; different changes on both sides conflict. Disjoint selected-field changes can merge only when the codecs and current per-field baselines prove independence. Preserve current unselected and read-only fields. Same-field multiselect conflicts compare complete canonical sets/sequences; do not silently union a user's removal away. No baseline plus divergent values requires review.

Persist phases separately: gather bounded metadata/values → validate scope/schema → record accepted desired document and source revision → publish/verify working copy → prepare provider intent → reread provider guard → one bounded mutation → reread provider result → publish/verify canonical working copy and optional v1 event → commit baseline and receipt. A saved editor candidate remains a durable obligation until verified provider/destination convergence or explicit reviewed cancellation/resolution. In particular, do not delete its full desired document in the gap between verified file upload and creation of the provider intent.

Fulcra file handling must use complete bounded published history with explicit uploaded/archived/deleted states, exactly one current uploaded head, immutable version IDs, strict metadata validation, and bounded UTF-8 downloads. Archived/deleted matches are evidence, never current readback. Capture full history before allocation, reread immediately before transfer, and check newly observed IDs/deletions after delivery. Preserve every intervening version reference alongside the full accepted candidate. Missing/ambiguous/malformed history or unavailable retained bytes is an unresolved condition, not an empty list or success. Do not resend an upload whose own receipt is deleted.

No atomic cross-service transaction or universal compare-and-swap is claimed. Attio requests must not invent If-Match/version behavior. Recheck immediately before mutation and read back afterwards; reconcile 409, response loss, normalization and concurrent third values by fresh evidence. Recognize an already applied deterministic result and continue verification rather than replay. Never roll back an unrelated human edit to make the expected hash match. A race in the last read-to-write interval remains a documented API limitation; persist before/desired/observed evidence and detect observable divergence.

Conflicts retain immutable readable Attio, accepted Fulcra, and intervening working-file versions with hashes/IDs. Resolution commands bind conflict ID, current working-file revision, current provider hash/schema fingerprint, and the server-owned selected evidence ID/hash. Reject stale tokens, forged references, or missing evidence; reread before applying the chosen version. Keep prior accepted versions and references through conflict refresh, temporary access loss, invalid files, restarts, and schema conflicts. One blocked entity must not prevent healthy selected entities from progressing.

Missing records/notes, merges, access loss, and local file deletion do not authorize provider deletion or creation. Keep imports and surface inaccessible/deleted/merged state separately. Do not automatically follow a merge to an unselected record. Local exclusion/pause is supported; destructive Attio delete is outside scope, and no Notion-style recoverable archive is invented for Attio entities.

## Creation and uncertain outcomes

New records require an explicit create-enabled object and a reviewed typed field ledger satisfying its required attributes. Prefer an owner-approved existing unique integration-key attribute containing a connection-scoped operation UUID. Do not silently create that schema. The [record upsert endpoint](https://docs.attio.com/rest-api/endpoint-reference/records/upsert-a-record), PUT `/v2/objects/{object}/records` with `matching_attribute`, matches a unique attribute and can update an existing record; use it only with the designated integration key and exact validated mapping, never as an email/name-based overwrite shortcut. After a lost response, query/recover the exact key and inspect current values before binding success. A unique key prevents duplicate identity, but does not authorize replaying the original fields over intervening edits: different current values become a conflict. Once bound, normal writes use the existing record-ID endpoint and field guards.

When there is no suitable unique key, creation can use a single POST with a durable pre-call guard and an explicitly configured recoverable marker field. Its absence from a bounded search does not prove the POST failed. If a safe marker cannot be stored/searched, disable automated record creation and offer existing-record mapping; do not claim idempotency from a local UUID alone. Existing list-entry creation is deferred until the workspace's duplicate-parent-entry rules and required fields have a verified recovery strategy; editing existing entries is included.

Note revision creation has a deterministic operation marker in both its title and provenance body. Before POST, persist a nonexpiring create intent and publish/read back a durable attempt guard. Across restarts, once an attempt may have been sent, enumerate the approved parent's paginated notes and recover one exact matching marker and payload. Zero matches remains `creation_uncertain`; multiple matches or changed content requires review. Never blindly repeat an uncertain POST, even when the first attempt might have crashed before transmission. A definitive rejection may prepare a new attempt only after validation and a fresh guard. Do not use undocumented idempotency headers. A successful response must be validated against the expected workspace/parent, then independently GET-read and verified before binding completion.

## Native state, pagination, scheduling, and index

Use the existing serialized native controller and persisted phases, with the existing deployment/owner encryption context. Keep baseline and accepted-work evidence nonexpiring. Transient staging expiry must not erase recovery obligations. Version manifests and provide compatible migration/restart behavior; do not reset established state, copy another deployment's controller, or silently enable a new connection during upgrade.

Design partitioned baseline/mapping state from the start. Keep a compact encrypted controller manifest with scope, shard references, scheduling and active accepted-write intents; store independently encrypted, versioned mapping/baseline shards and immutable source/conflict snapshots in the owner’s Fulcra files. Bind every shard to the same deployment/owner/connection encryption context and exact immutable ID/hash. Publish/read back each replacement shard before advancing its reference; interrupted replacement must leave the prior shard and pending obligation recoverable. Do not load the whole selected collection into one native step. Read encrypted baseline shards through an explicit bounded shard reader that accounts for encryption expansion; do not send128KiB shards through the current64KiB working-copy reader.

The root navigation file is also byte-bounded: it links to paged/sharded child indexes for records and note lineages rather than embedding2,000 rows. Partition working files into bounded shard subfolders, discover each folder with its actual endpoint limit, and persist coverage before advancing. Do not reuse the existing500-item folder list or64KiB file reader as if it were an unbounded full-collection scan. Verify root/child index links and semantic no-churn behavior at the target load.

The capacity acceptance target is **1,000 selected records plus 1,000 selected note lineages per connection in synthetic load/restart tests**, using byte-bounded shards (proposed at most64 entities/128KiB plaintext per shard), at most32 editable attributes per entity,48KiB typed documents,24KiB note drafts, and at most5 accepted queued edits. These are connector choices rather than Attio platform maxima, and must be adjusted against measured encrypted expansion before implementation acceptance. Retain the existing512KiB compact connection manifest and total native controller/staging byte budgets; do not turn the entire1,000+1,000 mapping set into inline controller state. Bound individual provider responses to2MiB and exact-path published history to500 versions; an exhausted budget holds the affected item with an explicit action rather than truncating or deleting it. Calculate worst-case accepted intent/conflict/index expansion before accepting an edit. A larger live collection is never enabled solely because a synthetic capacity test passed.

Default note history is a proposed 30-day window, shown for approval; deeper history is an explicit choice and may require another bounded connection. Records are stateful snapshots, so explain that their current fields are not filtered by an invented recent-touch timestamp. New records/notes beyond mapping capacity are reported as skipped/unmapped, never partially accepted without disclosure. Oversized existing entities remain read-only with source links and precise capacity errors.

Paginate schema, object/list discovery, records/entries and parent-filtered notes using their actual endpoint contracts. Persist offsets/cursors and dedupe stable IDs; reject malformed/repeated pagination and incomplete pages. Offset pagination under concurrent inserts is not a transaction: perform bounded reconciliation epochs/overlap and repeat coverage, never infer deletion solely from absence in one list pass. A failed page leaves its checkpoint unresolved. Webhooks are deferred; later signed hints may only enqueue already authorized resources and never expand scope.

Parse Retry-After as an HTTP date first when appropriate and as valid delta seconds for interoperability. Persist the resulting not-before time rather than sleeping through a native step. Past dates use a small positive delay; malformed/missing values use bounded exponential backoff with jitter. A valid future reset must not be clamped earlier merely to fit a step deadline. Treat 401/403 as authorization/access failures; 429 and retryable 5xx/network errors keep intents. Writes with unknown outcomes enter reconciliation before any replay. Start below documented workspace rate ceilings, coordinate this deployment's reads/writes, and expect limits to be reduced; do not promise to control other apps sharing the workspace.

Publish a connector-owned `index.md` in the connection's live folder. It lists verified records/entries, note source/revision lineage, writable/read-only capabilities, stable copy-update time, source links, current verified file/v1 revision, conflicts, retained intervening choices, uncertain creates, inaccessible/quarantined/schema/capacity conditions, and exact next actions. It must not claim that a pending candidate is the verified current copy. Sanitize labels and links; source prose is data, not agent instructions. Compare semantic index content and verify current uploaded bytes to prevent no-op version churn. Index retries must yield to document work.

The app provides typed editors, a separate note-source view and revision draft, three-version conflict review when applicable, and clear queued/verified/error states. Keep a draft on a rejected request; disable saving invalid/oversized drafts without discarding them. Show “Publish linked note revision” instead of “Replace note.” A failed evidence download leaves its immutable ID visible and disables only that unavailable resolution choice. Do not render imported HTML as trusted markup or fetch source-provided URLs with bearer credentials.

## Acceptance and tests

Synthetic tests are necessary but do not establish live Attio acceptance. Each supported codec and operation needs an explicit test row; unsupported capabilities remain honestly labeled read-only or unverified.
